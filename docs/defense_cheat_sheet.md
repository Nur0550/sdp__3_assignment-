# Шпаргалка для устной защиты (Oral Defense Cheat Sheet)

Устная защита составляет **50% оценки**. Ниже собраны ответы на все вопросы, которые может задать преподаватель.

---

## 1. В чём суть вашего проекта и предметная область?
- **Тема:** Аудиосистема воспроизведения музыки (**Music Playback System**).
- **Суть:** Мы воспроизводим разные типы контента (одиночные треки `Song` и упорядоченные плейлисты `Playlist`) через различные аудио-движки (`AudioEngine`), ориентированные на разные форматы файлов:
  - `.wav`, `.aiff` — встроенный движок Java Sound API (`JavaSoundEngine`);
  - `.mp3`, `.ogg`, `.aac` — процесс `ffplay` (`FFmpegEngine`);
  - `.mid`, `.midi` — устаревший сторонний плагин Winamp (`LegacyWinampPlugin`), подключённый через адаптер `LegacyWinampAdapter`.

---

## 2. Зачем здесь паттерн Bridge?
**Проблема комбинаторного взрыва (Combinatorial Subclass Explosion):**
Если бы мы не разделили абстракцию и реализацию, нам пришлось бы создавать отдельный класс под каждую комбинацию:
- `WavSong`, `Mp3Song`, `MidiSong`
- `WavPlaylist`, `Mp3Playlist`, `MidiPlaylist`
- При появлении 3-го типа контента (`RadioStream`) и 4-го движка (`FlacEngine`) мы получили бы $3 \times 4 = 12$ классов.

**Решение через Bridge:**
Мы разделили две независимые иерархии:
1. **Abstraction (Что воспроизводим):** `Playable` $\rightarrow$ `Song`, `Playlist`
2. **Implementor (Как воспроизводим):** интерфейс `AudioEngine` $\rightarrow$ `JavaSoundEngine`, `FFmpegEngine`, `LegacyWinampAdapter`
Вместо умножения классов ($N \times M$) мы получаем сложение ($N + M = 2 + 3 = 5$ классов).

---

## 3. Зачем здесь паттерн Adapter и почему Bridge один не справляется?
- **Почему Bridge один не решает проблему:**
  Bridge требует, чтобы все конкретные реализации подчинялись общему интерфейсу `AudioEngine`. Но у нас есть сторонний готовый класс `LegacyWinampPlugin`, исходный код которого мы **не можем изменять**.
- **В чём реальная несовместимость (Genuinely Incompatible):**
  1. **Имена и сигнатуры методов:** 
     - Вместо `load(path)` у него `openTrack(path, sampleRate)` — требует обязательный дополнительный параметр частоты дискретизации (`int sampleRate`).
     - Вместо `play()` у него `startPlayback()`.
     - Вместо `stop()` у него `stopPlayback()`.
  2. **Типы и диапазоны параметров:**
     - В `AudioEngine` громкость линейная `double [0.0, 1.0]`.
     - В `LegacyWinampPlugin` громкость задаётся как децибелы `float [-60.0, 0.0] dB`. Адаптер производит логарифмический пересчёт: $\text{gainDb} = 20 \cdot \log_{10}(\text{level})$.
  3. **Механизм обработки ошибок:**
     - `AudioEngine` по контракту выбрасывает `AudioException`.
     - `LegacyWinampPlugin` возвращает отрицательные статус-коды: `-1`, `-2`, `-3`, `-4`, `-5`, `-6`.
- **Что делает `LegacyWinampAdapter`:**
  Оборачивает `LegacyWinampPlugin`, реализует `AudioEngine`, передаёт дефолтный `sampleRate = 44100`, преобразует уровень громкости и транслирует все числовые коды ошибок в единое исключение `AudioException`. Внутренние детали плагина наружу не утекают.

---

## 4. Почему Adapter один не решил бы задачу?
Adapter адаптирует один класс к одному интерфейсу. Он не разделяет иерархию управления контентом (`Song`, `Playlist`) от реализации вывода звука. Без Bridge нам всё равно пришлось бы писать адаптированные классы под каждый тип контента.

---

## 5. Как соблюдается принцип Open/Closed (OCP) на обеих осях?
- **Ось Abstraction:** Мы можем добавить `Podcast` или `RadioStream`, унаследовавшись от `Playable`. При этом ни один класс движка или селектора не изменится.
- **Ось Implementor:** Мы можем добавить `SpotifyEngine`, реализовав `AudioEngine`. При этом ни `Song`, ни `Playlist`, ни другие движки не изменятся.

---

## 6. Какой модуль сложности выбран (Complexity Module)?
**Dynamic Implementor Selection (Динамический выбор реализации):**
- Класс `AudioEngineSelector` анализирует расширение передаваемого файла в runtime:
  - `.mid`, `.midi` $\rightarrow$ `LegacyWinampAdapter`
  - `.mp3`, `.ogg`, `.aac` $\rightarrow$ `FFmpegEngine`
  - `.wav`, `.aiff`, по умолчанию $\rightarrow$ `JavaSoundEngine`
- Клиентский код (`Song`, `Playlist`) **никогда не хардкодит** конкретную реализацию движка.

---

## 7. Какие тесты написаны?
Написано **43 unit-теста на JUnit 5**:
1. `SongTest` (8 тестов) — проверяет порядок делегирования вызовов (`load` $\rightarrow$ `setVolume` $\rightarrow$ `play`), метод `stop`, проброс `AudioException`.
2. `PlaylistTest` (10 тестов) — проверяет воспроизведение с пониженной громкостью (0.85), циклический переход `next()` с возвратом к началу (wrap-around), валидацию конструктора.
3. `LegacyWinampAdapterTest` (15 тестов) — проверяет корректную подстановку `sampleRate = 44100`, логарифмическую конвертацию громкости, валидацию входных диапазонов, трансляцию всех статус-кодов (`-1`...`-6`) в `AudioException` и отсутствие утечки имени плагина в текст ошибок.
4. `AudioEngineSelectorTest` (10 тестов) — проверяет выбор движков по разным расширениям и регистрам символов.

**Результат прогона тестов:**
```
Tests run: 43, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

## 8. Какое ограничение есть у данной архитектуры (Design Limitation)?
Движок привязывается к объекту `Playable` в момент создания. Если потребуется сменить устройство вывода или движок прямо «на лету» во время воспроизведения того же трека (hot-swapping без создания нового объекта), текущий дизайн потребует добавления сеттера `setEngine()` и потокобезопасной синхронизации состояния.
